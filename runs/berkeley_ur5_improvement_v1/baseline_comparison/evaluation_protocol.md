# Как оценивать наши траектории

Для двух текущих сцен Berkeley я рекомендую визуальный разбор и набор взаимодополняющих метрик. Ранжирование одной цифрой скрывает причину ошибки: верное направление может сочетаться с ранним подъёмом, правильной конечной длиной и неправильной дугой.

## Общий контракт

Одинаковые 24 ID, t0, история, instruction, реальные будущие RGB и независимый tracker reference. Оценка только будущего: +0,2…+2,0 с. Физическое соответствие шагов `[2,5,…,29]` зафиксировано. Пространственный коэффициент ×1/3 — отдельная операция вокруг собственного P(t0); он не меняет время.

Все методы получают одинаковую общую маску видимости reference. Выход за кадр учитывается как ошибка. Некорректный/неполный прогноз нельзя улучшать исключением его неудобных точек. Для каждого метода публикуется coverage и точное число оцениваемых пар. Все три независимые P8-группы показаны; лучший отдельный point ID не заменяет полный результат.

Текущий reference получен AllTracker, это не ручная разметка. Для утверждений о точности порядка 2–3 пикселей стоит независимо разметить несколько точек и кадров. Старые и новые input freezes сохранены; вычисление новых baseline использует только историю. Выбор лучших веток по уже просмотренному будущему этих двух сцен является исследовательским, а не независимым test результатом.

## Визуальная оценка

На одинаковых настоящих кадрах ставить рядом reference, static, CV и модель. В каждой сцене проверять:

1. Направление: объект поднимается, переносится, поворачивается в нужную сторону.
2. Форму: траектория не делает лишнюю петлю и не начинает размещение раньше реального объекта.
3. Размах и скорость: точки остаются на объекте на промежуточных кадрах.
4. Время: начало подъёма, поворот, остановка совпадают по реальным секундам.
5. Согласованность: точки одного объекта движутся вместе, три P8-группы не предсказывают разные действия.

Для следующего набора сцен полезен слепой попарный просмотр с одинаковыми масштабами и заранее определёнными категориями «совпадает / частично / не совпадает». Сейчас сохранены качественные наблюдения; числовая экспертная шкала задним числом не присвоена.

## Основные числа

Официальный MolmoMotion использует ADE, FDE и PWT в 3D: PWT усредняется по порогам 1, 2, 5, 10 и 20 см. Это подходящая основа для будущего benchmark с проверенной 3D-калибровкой. [Первичный источник: статья, §4.1 и Appendix C.4](https://arxiv.org/html/2606.18558v1#S4.SS1).

В нашем текущем сравнении разных K основным численным пространством служит 2D с единым reference:

| Метрика | Что показывает | Как публиковать |
|---|---|---|
| ADE 2D | Средняя L2 ошибка по всем видимым point/time | px и доля диагонали кадра; 640×480 имеет диагональ 800 px |
| FDE 2D | Ошибка последнего момента +2 с | Вместе с ADE, а не вместо неё |
| PWT@5/10/20/40 px | Доля point/time с ошибкой строго меньше порога | Каждый порог отдельно; шкала нативных пикселей явно указана |
| Медиана / P90 ошибки | Типичная ошибка и тяжёлый хвост | Вместе с числом валидных пар |
| Ошибка по времени E(t) | Раннее расхождение, разворот, плохой конец | Все десять времён, дополнительно E@0,2/0,4/1/2 с |

PWT в нативных пикселях — наша явно заданная 2D адаптация; это не официальный TAP-Vid/Average Jaccard score. Из двух агрегатов при выборе рабочей ветки я смотрел бы сначала на визуальный характер движения, затем на ADE/PWT, а FDE использовал бы для контроля конечного состояния. Весить их в произвольную единственную оценку сейчас не нужно.

3D ADE/FDE/PWT в сантиметрах публикуются отдельно как 3D_est, обусловленные оценённой K, на общей маске валидной sensor Z. Они полезны внутри фиксированной геометрии. Разные предполагаемые камеры меняют XYZ самого reference, поэтому сравнение 3D разных K без оговорки может награждать изменение масштаба. Для главного 3D рейтинга нужна одна проверенная калибровка и система координат для всех методов.

## Метрики, объясняющие ошибку

- Направление: медианная угловая ошибка вектора движения на физически совпадающих шагах. В реализованной 2D диагностике шаги reference >1 px считаются движущимися; отсутствующее движение прогноза уменьшает direction coverage и не получает выдуманный угол.
- Скорость: MAE модулей projected скорости в px/s.
- Длина пути: медиана L_pred/L_reference на полностью видимых траекториях. Отдельно вычислено отношение длины конечного смещения. Эти величины различают длинную дугу и правильный конечный размах.
- Жёсткость: медиана/P90 изменения попарных 3D расстояний относительно собственного t0, в мм, отдельно внутри и между P8-группами. Для чашки и бутылки это физическая проверка. Статичная ошибка тоже может иметь идеальную жёсткость, поэтому эту метрику всегда читать вместе с точностью движения.
- Ошибка фазы: для будущего benchmark заранее разметить начало подъёма/поворот/остановку и измерять отклонение времени в секундах. На текущих данных она оценена визуально; отдельная автоматически вычисленная event timing accuracy не заявлена.

DTW, подобранный alpha, сдвиг времени и Procrustes можно использовать как дополнительные диагностические эксперименты. Основную оценку считать до этих подгонок: они способны скрыть именно ошибки масштаба, направления и времени, ради которых проводится эксперимент. Best-of-K допустим только как отдельный одинаковый для всех генеративных методов протокол; нынешние прогоны — один greedy ответ каждой группы. Опубликованный MolmoMotion benchmark использует best-of-5, поэтому его таблицу нельзя напрямую сопоставлять с нашими числами. [Протокол автора](https://arxiv.org/html/2606.18558v1#S4.SS1).

## Что оказалось лучшим

Среди MolmoMotion для чашки визуально лучшие — CASE-NOK×1/3 и CASE-NOK-STRICT×1/3. Все три группы в основном поднимаются, а не рисуют большую дугу размещения. Строгая версия немного лучше по ADE: 18,699 против 19,004 px; лучевой контроль лучше по FDE: 18,670 против 22,277 px. PWT@20 px также немного выше у лучевого контроля: 54,6% против 53,8%. Это близкие варианты с разным остаточным временным поведением, а не один безусловный победитель. Без ×1/3 ошибки остаются велики.

Для бутылки CASE-NOK×1/3 имеет наименьший ADE среди модельных вариантов: 42,275 px. CASE-AUGE×1/3 имеет лучший FDE: 34,255 px. Ни один не совпадает хорошо с промежуточным движением: дуга вправо начинается рано. PWT@10 px равен нулю у обоих; PWT@20 px около 11–12%. Строгая геометрия не исправила эту ошибку. H1 на первых восьми точках чашки и future-fitted oracle имеют отдельный контракт, поэтому они не смешаны с 24-point таблицей.

Среди всех текущих методов лучшая точность чашки у простого переноса объекта с единой медианной observed скоростью: ADE около 1,99 px, PWT@20 px 100%, попарные 3D расстояния сохраняются. Бейзлайн не получает будущих данных. Обычный CV даёт около 2,9 px. Для бутылки CV даёт около 11,0 px; общий перенос — около 11,3 px и 100% PWT@20 px. На просмотренных кадрах CV тоже ближе модели к объекту, хотя бутылке несколько не хватает скорости и точности позднего положения. Полные [числа](results.json), [таблица и видео](README.md).

Наше решение улучшает исходный MolmoMotion и добавляет проверенную подготовку данных, реальные модели, разные геометрические гипотезы и доказанную связь ShareRobot. Превосходство полного прогноза над простыми причинными baseline на этих сценах не получено. Поскольку все варианты используют общие точки и reference из нашей подготовки, сравнение оценивает forecasting после этой подготовки; оно не измеряет преимущество нашего grounding/tracking над другим end-to-end pipeline.

## Что нужно для общего вывода

Две сцены и 24 коррелированные точки одного объекта не являются 48 независимыми тестовыми примерами. Расширить набор эпизодов и фаз: подъём, ускорение, поворот, остановка и размещение. K-ветку и коэффициент выбрать на validation и закрепить до test. Ошибки агрегировать сначала по сцене, затем между сценами; доверительные интервалы оценивать по независимым эпизодам, а не по соседним точкам/кадрам. На длинном и нелинейном горизонте проверять, появляется ли преимущество языка и learned motion prior над постоянной скоростью.

Для текущего отчёта достаточная система: визуальные сравнения всех групп + ADE/FDE/PWT 2D + E(t) + direction/speed/path diagnostics + 3D жёсткость, с отдельными 3D_est метриками и coverage. Все численные сравнения здесь опираются на сохранённые реальные прогнозы; новые ML-вызовы не понадобились.
