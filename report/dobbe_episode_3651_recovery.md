## RGB и depth

Depth содержит 243 карты `192×256`, все значения конечные и положительные, диапазон в исходных единицах 0.05307–2.23242. Исходный RGB имеет размер `256×256`; у MP4 в контейнере 30 fps. Версия LeRobot объявляет 3.75 fps, поэтому её timestamps **не принимаются за время исходной записи**. Размер и формат проверены в [аудите](../runs/plex_dobbe_preflight/dobbe_3651_recovered_audit.json).

Для диагностического наложения использована гипотеза `u_depth=u_rgb`, `v_depth=(v_rgb+0.5)·192/256−0.5`. На боковых границах красной чашки в кадрах 0, 20 и 40 лучший горизонтальный сдвиг равен 0 px; медианный сдвиг каждой стороны равен 0 px, 90-й процентиль абсолютного сдвига 1–2 px. Сдвиг +10 px резко снижает сигнал на границе. См. [числовую проверку](../runs/plex_dobbe_preflight/dobbe_3651_cup_rgb_depth_alignment.json). Это сильное **локальное** свидетельство совмещения RGB и depth для чашки. Позднее чашка частично заслонена или выходит за кадр, и этот тест там существенно слабее. Он не доказывает точное преобразование всего изображения, отсутствие искажений или метрическую обратную проекцию. Разработчик Record3D [поясняет](https://github.com/marek-simonik/record3d/issues/31#issuecomment-1025113866), что приложение объединяет RGB и depth средствами Apple; для данной опубликованной записи всё равно нужна собственная проверка после обработки.

## Почему 3D-вход ещё не подтверждён

В целевом `labels.json` имеются только `xyz`, `quats`, `gripper`. В индексе опубликованного RGB-D архива — 28 434 внутренних файлов и **0 файлов `metadata`**; в опубликованном RGB ZIP и выборочном fine-tuning ZIP также не обнаружена калибровка. Это соответствует [официальным инструкциям по скачиванию](https://docs.dobb-e.com/software/readme-1/setting-up-the-datasets): предоставляются обработанные RGB и RGB-D релизы. При этом [официальный `process_from_r3ds.py`](https://github.com/notmahi/dobb-e/blob/main/stick-data-collection/process_from_r3ds.py) получает `K`, `w`, `h`, `fps`, `poses` и `initPose` именно из `metadata` исходного R3D. Отдельный [вопрос об intrinsics HoNY](https://github.com/notmahi/dobb-e/issues/2) подтверждает, что они не очевидны пользователю опубликованного набора.

Проверены три экспериментальных способа восстановить эффективную `K`:

1. Фиксированная пробная `K=(200,200,128,128)` и перебор осей для `labels` дают медианную ошибку перепроекции лучших осей 6.72 px по нескольким парам; по отдельным парам ошибка до 17.8 px. [Протокол](../runs/plex_dobbe_preflight/dobbe_3651_camera_pose_probe.json).
2. Совместная подгонка `fx,fy,cx,cy` и сдвига depth по сохранённым позам дала `fx≈174`, `fy≈199`, `cx≈154`, `cy≈155` и вертикальный сдвиг depth **−18.9 px**. Он не согласуется с прямой проверкой границ; на отложенных парах медианная ошибка достигает 8.98 px. Более гибкая подгонка осей и базиса камеры упёрлась сразу в несколько ограничений параметров. Это [диагностические](../runs/plex_dobbe_preflight/dobbe_3651_effective_k_fit.json) [результаты](../runs/plex_dobbe_preflight/dobbe_3651_joint_calibration_stress.json), не калибровка.
3. Подгонка общей `K` по жёсткости RGB-D соответствий без использования сохранённых поз тоже не идентифицирует её: `fx` и `fy` дошли до установленной верхней границы 600 px, а `cx,cy` заметно различаются между подмножествами. Улучшение 3D-невязки на отложенных парах мало. [Протокол](../runs/plex_dobbe_preflight/dobbe_3651_rgbd_self_calibration.json). При таком виде сцены и допущениях глубина сама по себе не дала устойчивую `K`.

Таким образом, сохранённые `xyz/quats` нельзя автоматически считать проверенным world↔camera преобразованием для MolmoMotion; преобразование осей и смысл depth также требуют сверки с исходным `metadata`. Числа подогнанной `K` нельзя подставлять в `[3,8,3]` как подтверждённые метры. Новый запуск MolmoMotion и ADE/FDE по Dobb·E не выполнены.

## Воспроизведение и минимальный недостающий артефакт

В рабочем каталоге `F:\AIRI_task\molmo-motion`:

```powershell
python scripts/download_dobbe_3651_lerobot.py
python scripts/index_dobbe_pick_place_labels.py
python scripts/match_dobbe_lerobot_to_hony.py
python scripts/extract_dobbe_3651_rgbd.py
python scripts/audit_dobbe_3651_recovered.py
python scripts/check_dobbe_3651_cup_alignment.py
python scripts/probe_dobbe_3651_rgbd_self_calibration.py
```

Скрипт извлечения использует ранее построенный [индекс](../runs/plex_dobbe_preflight/dobbe_depth_nested_index.json) split ZIP и скачивает только диапазоны трёх целевых членов, не весь RGB-D набор. Для `audit`/проверки alignment нужен `pyliblzfse` (`liblzfse`) в `F:\AIRI_task\.tools\lzfse`; также нужны `numpy`, `opencv-python`, `pyarrow`, `scipy` и `requests`.

Самый короткий путь к подтверждённой 3D-истории — получить `metadata` **именно исходного R3D** для `Pick_and_Place/Home15/Env1/2023-04-25--02-05-30` либо эквивалентные `K` опубликованного RGB, карту соответствия depth↔RGB и трактовку `poses`. Тогда можно независимо проверить перепроекцию нескольких неподвижных поверхностных точек между кадрами, восстановить точки чашки в координатах камеры `t0` и сформировать `[3,8,3]`. Никакой запрос авторам не отправлялся.
